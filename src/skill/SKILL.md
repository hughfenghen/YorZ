# YorZ Spec Drive Skill

将单个 YorZ spec 文档作为状态机执行，围绕 `plan`、`tasks`、`execute` 三阶段推进，并把状态持续写回文档。Agent 短跑即退，每次工作完整地读 md → 做事 → 写 md → 退出；md 是单一真相。

## 输入约定

- `spec_path`：**可选**，目标 spec 文档路径。
  - 显式给出时：典型位置 `docs/specs/*.md` 或 `.yorz/specs/<id>/spec.md`，直接更新该 spec。
  - 缺省时：进入「新建 spec」流程（见同名章节）。
- `mode`：可选，`plan|tasks|execute|auto`，默认 `auto`。
- 批注前缀：`！！！`

## spec 文档 frontmatter 规范

每个 spec md 顶部必须有 YAML frontmatter 记录元信息：

```yaml
---
stage: plan # plan | tasks | execute
last_action: 简述上一次动作
updated_at: 2026-06-14 # YYYY-MM-DD
summary: 一句话概要，供列表/索引视图展示
---
```

- 字段顺序固定为 `stage` → `last_action` → `updated_at` → `summary`，每个字段独占一行，禁止嵌套
- 键名使用英文，便于工具静态解析；字段值允许中文
- `summary` **必填**，长度 ≤ 200 字符，不允许空字符串
- 时间字段使用 `YYYY-MM-DD`，不引入时区与时间部分
- 缺失任意字段时，先补齐再继续
- skill **不解析**旧 `## 流程状态` 章节；遇到使用旧格式的 spec，按此规范一次性迁移并删除该章节

## 全局硬约束

- 仅更新目标 spec 文档，不修改无关文档。
- 每次写回文档都必须更新 frontmatter 元信息：`stage` / `last_action` / `updated_at` / `summary`。
- 若以下章节不存在，先补齐再继续：
  - `## 现状分析`
  - `## 技术实现方案`
  - `## 待确认问题`
  - `## 任务清单`
  - `## 执行记录`
- 若在已有 spec 中识别到"新增/扩展需求"或"新增 bug"（无论来自正文变更或 `！！！` 批注），必须将 frontmatter `stage` 立即切回 `plan`，并在 `last_action` 记录"变更重开流程"。
- 变更重开后，必须仅针对新增内容重新走完 `plan -> tasks -> execute`：先补充分析与确认，再拆任务并执行；未受影响的既有结论/任务可保留，但受影响任务必须重新评估与改写。
- 执行任务时若涉及代码改动，必须只改动与任务相关的最小范围；每次写回都同时更新 frontmatter 元信息。

## 自动模式判定顺序（严格按顺序）

1. 若 `spec_path` 缺省，进入「新建 spec」流程并以 `plan` 起步。
2. 否则，若识别到新增/扩展需求或新增 bug，进入 `plan`（重开流程）。
3. 否则，若文档存在任意 `！！！` 批注，进入 `tasks`。
4. 否则，若 `## 待确认问题` 下存在有效条目（非 `- 暂无`），停止推进并等待人工批注。
5. 否则，若存在未完成任务（`- [ ]`），进入 `execute`。
6. 否则，若 `## 技术实现方案` 为空或明显不完整，进入 `plan`。
7. 否则，进入 `tasks` 生成或刷新详细任务清单。

## 阶段行为

### 阶段一：plan

理解文档，分析现有代码，编写技术实现方案，更新到当前文档中；需要确认的问题以列表格式写入文档，待用户后续会进行审阅批注；暂时只需更新文档，不要实施代码。

- 目标：输出 `现状分析`、`技术实现方案`、`待确认问题`。
- `待确认问题` 必须使用无序列表；无问题时写 `- 暂无`。
- 禁止：输出任务清单格式 `- [ ]`。
- 若误生成 `- [ ]`，写回前必须改为无序列表 `- ` 或移除。

### 阶段二：tasks

根据批注内容（`！！！` 前缀）更新文档中的技术方案；审查批注内容是否正确解答了 `待确认问题`，是否会与目标或技术方案产生新的冲突或歧义；若批注或正文改动引入了新增/扩展需求或新增 bug，则必须先切回 `plan`，补充 `现状分析`/`技术实现方案`/`待确认问题` 后再继续；如果存在冲突或歧义，则回退到 `plan` 阶段，更新到文档 `待确认问题` 中，退出执行，等待重新批注；否则将技术方案拆解为详细的可执行任务（格式：`- [ ] 任务x`），写入文档；然后进入 `execute`。

- 输入：读取并消费所有 `！！！` 批注。
- 批注消费规则：
  - 将批注意图合并进 `技术实现方案` 与 `任务清单`。
  - 处理完成后删除对应 `！！！` 文本。
- 产出任务清单要求：
  - 仅使用 `- [ ]`。
  - 每项任务包含"动作 + 对象 + 验收点"。
  - 禁止泛化任务（如"完善功能""优化逻辑"）。
- 自动衔接：若 `待确认问题` 为 `- 暂无`（或为空），在同一轮继续进入 `execute`。

### 阶段三：execute

理解文档内容，然后执行文档中的任务，每完成一个任务后勾选文档中的任务状态。

- 顺序执行 `任务清单` 中未完成项。
- 执行中若发现新增/扩展需求或新增 bug，立即停止继续勾选，切回 `plan` 并记录重开原因。
- 每完成一项后立刻：
  - 将该项从 `- [ ]` 改为 `- [x]`。
  - 在 `执行记录` 增加一条结果（改动点、验证方式、阻塞项若有）。
- 默认执行验证：
  - 若仓库存在可用测试/构建命令，默认执行并记录结果。
  - 若当前环境无法执行验证，记录原因并保留相关任务未完成或追加阻塞记录。

## 新建 spec

当 `spec_path` 缺省时执行以下流程，由 skill 自动生成路径与初始骨架：

1. **提炼摘要**：从用户首轮输入中提炼需求摘要，生成 `summary-name`：
   - 形式：kebab-case，仅允许字符集 `[a-z0-9-]`
   - 长度 ≤ 40 字符
   - 不以数字开头
2. **判定 type**：从 `feat`（新功能）/ `refct`（重构/重写/抽取）/ `fix`（修复缺陷）中选择：
   - 分类明确时直接采用
   - 不确定时**显式询问用户**；若需兜底则取 `feat`
3. **生成 id**：`YYMMDD.<type>.<summary-name>`
   - `YYMMDD` 取当前日期
   - 例：`260614.feat.spec-frontmatter`
4. **生成路径**：`.yorz/specs/<id>/spec.md`（每个 spec 一个独立子目录，方便附件/截图/中间产物共置）
5. **id 冲突处理**：若 `.yorz/specs/<id>/spec.md` 已存在，将 `<id>` 追加 `-2`、`-3` …… 数字后缀，直至无冲突
6. **初始化文档**：
   - 写入 frontmatter（`stage: plan`、`last_action: 新建 spec`、`updated_at: <YYMMDD 对应日期>`、`summary: <首轮需求一句话概要>`）
   - 补齐六大空章节：`## 背景` / `## 需求` / `## 现状分析` / `## 技术实现方案` / `## 待确认问题` / `## 任务清单` / `## 执行记录`
7. **进入 plan 阶段**：随即按阶段一规范继续工作。

> skill 自身不写入 `.gitignore`；是否将 `.yorz/specs/` 纳入 git 跟踪由用户自行决定。

## 待确认问题判定

- 仅解析 `## 待确认问题` 章节。
- 视为"未决"的条目：`- ` 开头且内容不是 `暂无`。
- 当存在未决条目时，禁止自动进入 `execute`。

## Markdown 格式化约定

为保证 spec 文档结构稳定、易被工具与人审阅：

- frontmatter 元信息按「spec 文档 frontmatter 规范」一节约束写入；字段顺序固定，禁止嵌套与额外字段（如需扩展请先更新本 skill）。
- 时间字段使用 `YYYY-MM-DD`（如 `updated_at: 2026-06-14`），不引入时区与时间部分。
- 每次写回 spec md 后，**应在仓库支持的条件下运行 Markdown formatter**（优先使用项目根的 `prettier`，例如 `npx prettier --write <spec_path>`）；若仓库未配置 prettier，则跳过并在执行记录中说明。
- formatter 必须保留 YAML frontmatter 不变。
- 任务清单仅使用单层 `- [ ]` / `- [x]`，避免缩进与嵌套以利 formatter 稳定。

## 与 YorZ 工作流的关联

- 本 skill 不依赖 YorZ Service / GUI 也能独立工作：Agent 直接读写 `spec_path` 即可。
- 当 YorZ Service 在线时，Agent 写回 md 会被 Service 的 FS Watcher 感知并推送给 GUI；Agent 仍然以"短跑即退"为原则。
- 如需用户介入（待确认问题、决策、Review），Agent 把信息写回文档对应章节后立即退出，由用户人工补齐 `！！！` 批注或由 Service 拉起下一次执行。

## 输出优先级

1. 先保证状态正确（frontmatter 元信息更新、章节齐全）。
2. 再保证结构正确（列表格式、任务格式）。
3. 最后保证内容质量（可执行、可验收、可追踪）。
