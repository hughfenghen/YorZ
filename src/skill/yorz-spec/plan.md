# 阶段一：plan

理解文档，分析现有代码，编写技术实现方案，更新到当前文档中；需要确认的问题以列表格式写入文档，待用户后续会进行审阅批注；暂时只需更新文档，不要实施代码。

## 目标

- 输出 `## 现状分析`、`## 技术实现方案`、`## 待确认问题` 三节。
- `待确认问题` 必须使用无序列表；无问题时写 `- 暂无`。
- 禁止：输出任务清单格式 `- [ ]`。
- 若误生成 `- [ ]`，写回前必须改为无序列表 `- ` 或移除。
- 若 `## 追加任务` 存在 `- [open] [feat|refct|fix] ...` 条目，必须将其纳入 `## 现状分析` / `## 技术实现方案` / `## 待确认问题` 的分析范围；按类型差异化处理：
  - `[feat]`：重在范围拆解（新增能力的边界、用户故事、影响章节）。
  - `[refct]`：重在影响面与回归（被重构模块的依赖图、潜在破坏点、保留行为的回归手段）。
  - `[fix]`：重在根因与最小修复（复现路径、根因定位、最小代码改动半径）。
- plan 阶段**不修改** `## 追加任务` 中条目的状态标记，仅消费其内容。

## 候选项硬约束

每条问题**若**给出候选项，则必须**恰好** 1 个候选项以 ` (推荐)` 结尾；候选数量不做强制下限。无法或不必枚举（如概念澄清、错别字确认、开放性补全）时，在问题正文末尾追加 `（自由文本）` 后缀，显式声明该条退化为自由文本条目。

## 待确认问题结构

`## 待确认问题` 章节中，每条问题均为一级 `- ` 列表项；可选地在其下提供候选答案作为二级 `  -` 子列表（注意是 2 个空格缩进），并在恰好 1 个候选项尾部追加 ` (推荐)`：

```
- 候选答案的展现形式应采用哪种？
  - 嵌套子列表
  - 表格 (推荐)
  - 自定义 YAML 块
```

对于无法/不必枚举候选答案的问题（澄清、确认错别字、开放补全等），不要硬凑候选项，而是在问题正文末尾追加 `（自由文本）` 后缀显式声明退化：

```
- release notes 文案应该怎么写？（自由文本）
```

- 候选项采用单选语义：不引入"多选"概念；**给出候选项的问题必须恰 1 个 `(推荐)` 标记**，0 个或 ≥ 2 个均视为 Agent 输出违规，必须自检修正。
- 候选项 label 不限字符长度，GUI 端以 CSS 自适应换行处理。
- 推荐项必须放在候选项中已有的某个选项尾部，不要新增"以推荐项为名"的额外条目。
- 问题正文末尾的 `（自由文本）` 后缀是 GUI 强制 freeform 渲染的显式信号；不带后缀且无候选项的旧形态作为向后兼容，亦按 freeform 渲染但建议补齐后缀。
- 用户在 GUI 中提交答复时，结果会作为一个 `## 用户批注` 段落追加到 spec 末尾，每条答复一段 `> 引用 + ！！！备注` 块；该章节的清理时机见 [tasks 阶段](./tasks.md)。

## 产出前自检 checklist（写回 `## 待确认问题` 之前**逐条核对**）

- [ ] 是否每条 `- ` 一级问题都满足"要么有 ≥ 1 个 `  -` 二级候选项且恰 1 个 `(推荐)`，要么以 `（自由文本）` 结尾"？
- [ ] 候选项是否都用 `  -`（2 空格 + `-`）二级列表表达，**不是**散文段、**不是**表格、**不是**单层 `-`？
- [ ] 是否避免新增一条"以推荐项为名"的额外条目（推荐项必须是已有候选项之一的尾缀）？
- [ ] `(推荐)` 与候选项文本之间是否只有 1 个空格、且 `(推荐)` 严格出现在尾部（不含其它后缀）？
- [ ] 若全无可枚举候选，是否已加 `（自由文本）` 后缀（注意是全角括号）？

任意一项不满足，必须在写回前回头改正。

## 正反例

### 正例 ✅

```
- 候选答案的展现形式应采用哪种？
  - 嵌套子列表
  - 表格 (推荐)
  - 自定义 YAML 块

- release notes 文案应该怎么写？（自由文本）
```

### 反例 ❌ 1：有候选项但缺 `(推荐)`

```
- 候选答案的展现形式应采用哪种？
  - 嵌套子列表
  - 表格
  - 自定义 YAML 块
```

修正：给且**只给** 1 个候选项追加 ` (推荐)`。

### 反例 ❌ 2：多个 `(推荐)`

```
- 候选答案的展现形式应采用哪种？
  - 嵌套子列表 (推荐)
  - 表格 (推荐)
  - 自定义 YAML 块
```

修正：仅保留 1 个 `(推荐)`，删除其它的。

### 反例 ❌ 3：无候选项又无 `（自由文本）` 后缀

```
- release notes 文案应该怎么写？
```

修正：要么补齐候选项 + `(推荐)`，要么在问题正文末尾追加 `（自由文本）`。

### 反例 ❌ 4：用散文段写候选项

```
- 候选答案的展现形式应采用哪种？候选包括嵌套子列表、表格（推荐）、自定义 YAML 块。
```

修正：把候选项拆成 `  -` 二级列表项，每行 1 个。

### 反例 ❌ 5：新增一条"以推荐项为名"的额外条目

```
- 候选答案的展现形式应采用哪种？
  - 嵌套子列表
  - 表格
  - 自定义 YAML 块
  - 推荐：表格
```

修正：去掉"推荐：…"那条，把 `(推荐)` 直接追加到「表格」候选尾部。
