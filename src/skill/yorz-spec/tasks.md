# 阶段二：tasks

根据批注内容（`！！！` 前缀）更新文档中的技术方案；审查批注内容是否正确解答了 `待确认问题`，是否会与目标或技术方案产生新的冲突或歧义；若批注或正文改动引入了新增/扩展需求或新增 bug，则必须先切回 `plan`，补充 `现状分析`/`技术实现方案`/`待确认问题` 后再继续；如果存在冲突或歧义，则回退到 `plan` 阶段，更新到文档 `待确认问题` 中，退出执行，等待重新批注；否则将技术方案拆解为详细的可执行任务（格式：`- [ ] 任务x`），写入文档；然后进入 [execute](./execute.md)。

> 拆解任务清单时，若任务间存在依赖关系，可按需输出 mermaid 图表辅助理解——参见 [mermaid 图表输出指南](./mermaid.md)。

## 批注消费规则

- 输入：读取并消费所有 `！！！` 批注。
- 将批注意图合并进 `## 技术实现方案` 与 `## 任务清单`。
- 处理完成后**删除对应 `！！！` 文本**（避免下一轮再次触发 tasks 路由）。
- 在 tasks 阶段消费完所有 `！！！` 后，必须**整段删除** `## 用户批注` 章节，避免污染下一轮编号与索引。

## 产出任务清单要求

- 仅使用 `- [ ]`（不使用嵌套、不使用 `- [x]` 之外的状态符号）。
- 每项任务包含"动作 + 对象 + 验收点"三要素。
- 禁止泛化任务（如"完善功能""优化逻辑"）。

## 自动衔接

> 任务量不构成暂停理由：以下衔接规则与任务清单长度、改动半径无关。

- 若 `待确认问题` 为 `- 暂无`（或为空），且无新冲突 / 歧义，则在同一轮继续进入 [execute](./execute.md)。
- **同一轮衔接 execute 前后不得向用户追加任何"是否执行 / 是否继续"询问**；如需新输入，按 [全局硬约束](./rewrite-rules.md) 写入 `## 待确认问题` 触发重开。
- 若检测到批注引入新需求 / 新 bug，立即切回 plan（详见 [全局硬约束](./rewrite-rules.md) 的变更重开规则）。
