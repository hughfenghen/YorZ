# 阶段流程（plan / tasks / execute / done / new-spec）

## plan

理解文档，分析现有代码，编写技术实现方案，更新到当前文档中；需要用户介入的事项以三级标题写入 `## 待确认项`，待用户后续审阅批注；暂时只需更新文档，不要实施代码。

**目标：** 输出 `## 现状分析`、`## 技术实现方案`、`## 待确认项` 三节；禁止输出任务清单格式 `- [ ]`。

若 `## 追加任务` 存在 `- [open] [feat|refct|fix] ...` 条目，必须将其纳入分析范围；plan 阶段不修改 `[open]` 状态标记。

### 待确认项的三种类型

一个待确认项，要么让用户**抉择**，要么让用户**确认**，要么请用户**自由补充**：

| 类型     | 标记                | 语义                                                                                    | 何时用                |
| -------- | ------------------- | --------------------------------------------------------------------------------------- | --------------------- |
| 抉择型   | `[choice]`          | 给用户**选择权**：存在多个都可行、优劣取决于你拿不到的信息（业务优先级/外部约束）的方案 | 多方案差异大、难取舍  |
| 确认型   | `[confirm]`         | 给用户**否决权**：只有一个可行方案，但它有明显代价（技术债/影响面/不可逆）              | 单方案但影响重大      |
| 自由文本 | `（自由文本）` 后缀 | 请用户补一段开放说明                                                                    | 需要主观文案/开放意见 |

> 无标记且带有序候选，向后兼容视为 `[choice]`。

### 准入门槛（写入待确认项前必过的自检）

**第一道过滤器先于类型判断**：这个答案，你能否通过读代码、跑测试、查项目约定自己确定？

- **能** → 禁止写成待确认项，自己去查、去定，把决策+理由写进 `## 技术实现方案`（决策说明），不要打断用户。
- **不能**（决策依赖用户独有信息，或选错的返工不可逆）→ 才写成待确认项，并归入 choice/confirm。

> 待确认项是压力释放阀，不是免责声明。被你砍掉的判断不该凭空消失，要落成 `## 技术实现方案` 里的决策说明（决策 + 理由 + 被否决的备选）。

### 抉择型 [choice] 正确示例

```
### 5.1 [choice] 候选答案的展现形式应采用哪种？
1. 嵌套子列表
2. 表格 (推荐)
```

- 候选写一级有序列表；恰 1 个候选以 ` (推荐)` / ` （推荐）` 结尾。
- 空态与格式由 lint 的 `pending-questions/*` 规则保证。

### 确认型 [confirm] 正确示例

```
### 5.2 [confirm] 将 UserID 从 int 迁移为 uuid

**方案**：一次性迁移，双写过渡 2 周。
**影响**：🔴 需停机窗口；对外 /api/user 字段类型变更，客户端需同步。
```

- 只有 `**方案**` 与 `**影响**`（或 `**代价**`）两字段，**不列候选**。
- 影响行用红/黄语义标注严重度：🔴 breaking（破坏性/不可逆）、🟡 affected（有影响但可控）。
- 确认型 = "我要这么干了，除非你喊停" 的知会 + 急停按钮：放行是常态，用户否决才是例外。

### 确认型的否决语义（用户在 GUI 上如何回应）

用户对确认型只有两种回应：**确认放行** 或 **否决**。否决必须携带理由，并细分意图（GUI 渲染为嵌套单选）：

| 用户决策                  | 回写 `！！！选择：…`                 | 含义                   |
| ------------------------- | ------------------------------------ | ---------------------- |
| 确认，按此推进            | `确认，按此推进`                     | 接受代价，继续         |
| 否决·换方案               | `否决·换方案`                        | 原目标下另寻实现       |
| 否决·补约束               | `否决·补约束`                        | 用户补充你漏掉的硬约束 |
| 否决·弃目标·废弃当前目标  | `否决·弃目标·废弃当前目标，继续其余` | 该目标不做，其余照旧   |
| 否决·弃目标·放弃整个 spec | `否决·弃目标·放弃整个 spec`          | 整条 spec 作废         |

> 决策不改动 API：编码进批注的 `选择：…`（结构化意图）+ `备注：…`（理由）。tasks 阶段按下表消费。

### 图形化补充（plan 收尾子步骤）

方案文字定稿后、结束 plan 前，**必须**专门回看 `## 现状分析`、`## 技术实现方案` 两节做一次 mermaid 图形化补充（仅此两节，其它章节不动）：

- 加载 [mermaid.md](./mermaid.md)，先服从其**核心原则「图优先、精确信息折叠」**：表层给图（认知层），精确细节（路径、行号、类型/源码全文）折叠进 `<details>` 精确层，图与折叠互补不重复。
- 按选型表与「必须用图」触发词补图：分步/分支散文→flowchart，接口/类型定义→classDiagram；含「兼容性/影响范围」时出结构图并按红=breaking、黄=affected 语义配色。
- 这是一道独立聚焦的工序（不新增 stage）：把「想清楚方案 / 写成文字」与「回看补图」分开，避免图形化被跳过。补图完成后再结束 plan。

### 待确认项自检（plan 收尾子步骤）

方案与图形化定稿后、结束 plan 前，**必须**专门回看 `## 待确认项` 做一次自检（与「图形化补充」同构：把"写方案"与"回看校验"分开，避免自检被跳过）：

1. **准入过滤**：逐条问"能否自己查证？"——能则删除该条、把决策落进 `## 技术实现方案`（决策说明）。
2. **类型归类**：留下的每条明确标 `[choice]` 或 `[confirm]`（或 `（自由文本）`）；单一类型，不兼具。
3. **确认型补影响**：每个 `[confirm]` 必带 `**方案**` 与 `**影响**`（红/黄语义）；影响写不出来，说明它其实够不上确认型，降级或删除。

自检完成后再结束 plan。

空态整章仅一行斜体占位：

```
## 5. 待确认项

_暂无_
```

> 格式由 lint 的 `pending-questions/*` 规则保证；不确定时运行 `yorz lint` 查看报错。

## tasks

根据批注内容（`！！！` 前缀）更新技术方案；审查批注是否正确解答了待确认项；若引入新增/扩展需求或新增 bug，切回 plan；若存在冲突或歧义，回退 plan 并写入待确认项后退出；否则将技术方案拆解为可执行任务，写入文档，然后进入 execute。

### 批注消费规则

- 读取并消费所有 `！！！` 批注，将批注意图合并进 `## 技术实现方案` 与 `## 任务清单`。
- 处理完成后**删除对应 `！！！` 文本**，然后**整段删除** `## 用户批注` 章节。

### 确认型答复的消费

当批注含 `！！！选择：<决策>；备注：<理由>`（引用行的前缀 `待确认项`/`待确认问题` 皆可），按 `选择：` 分派下游行为，并**无论确认或否决都留痕**——在 `## 技术实现方案` 追加一行决策记录：`> 决策记录：<条目> —— 用户<决策>，理由：<理由>。`（决策记录不随 `## 用户批注` 删除而蒸发）：

| `选择：`                           | 下游行为                                                                                       |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| 确认，按此推进                     | 接受代价，落决策记录，继续拆任务                                                               |
| 否决·换方案                        | 切回 plan：原目标下另寻实现（新方案可能又产生 choice/confirm）                                 |
| 否决·补约束                        | 切回 plan：把理由当硬约束重算方案                                                              |
| 否决·弃目标·废弃当前目标，继续其余 | 从 `## 需求` 剔除该目标，落决策记录，继续其余目标                                              |
| 否决·弃目标·放弃整个 spec          | 落决策记录（作废），将 `stage` 置 `done` 终止，`last_action` 记「用户放弃整个 spec，标记终止」 |

### 任务清单正确示例

```
## 6. 任务清单

- [ ] 删除 src/foo.ts 中的 deprecatedFunc（验收：grep 无残留引用）
- [ ] 更新 index.ts 导出（验收：tsc --noEmit 通过）
```

> 每项任务包含"动作 + 对象 + 验收点"；仅使用单层 `- [ ]`；禁止泛化任务。

### `[manual]` 人工确认任务标记

对「需人工确认、Agent 不能自动完成」的事项，用 `- [ ] [manual] ...` 标注：

```
- [ ] [manual] 联系运维确认灰度窗口（验收：人工回复确认）
```

`done` 收尾判定**忽略**未勾选的 `[manual]` 项：只要其余非 manual 任务全部完成，即可收尾为 `done`，无需等待人工项被勾选（详见 execute 的「收尾为 done」）。

### 自动衔接

> 任务量不构成暂停理由：以下衔接规则与任务清单长度、改动半径无关。

若待确认项为 `_暂无_` 且无新冲突，同一轮继续进入 execute，**同一轮衔接 execute 前后不得**向用户追加任何"是否执行/是否继续"询问。

## execute

顺序执行 `## 任务清单` 中未完成项（`- [ ]`）。执行中若发现新增/扩展需求或新增 bug，立即停止，切回 plan。

> **执行过程中不得对用户做整批/中段元确认**：除"新需求/新 bug → 切回 plan"这一合法阻塞外，任务清单内部的任何疑问都必须以 `## 待确认项` 形式写回触发重开，禁止追加"是否继续 / 我是否应该执行下一项"等问句停顿。

### 每完成一项后立刻

- 将该项从 `- [ ]` 改为 `- [x]`。
- 在 `## 执行记录` 增加一条结果（改动点、验证方式、阻塞项若有）。

### 默认执行验证

若仓库存在可用测试/构建命令，默认执行并记录结果；若当前环境无法执行，记录原因。

### 追加任务 `[open] → [fixed]` 状态机

若本轮起因是 `## 追加任务` 中的 `[open]` 条目：每完成一个追加项，把状态标记从 `[open]` 改为 `[fixed]`（位置和正文保留不变），在 `## 执行记录` 追加一条结果。已 `[fixed]` 的条目保留作为历史，不删除。

### 收尾为 done

当 `## 任务清单` 不存在未完成的**非 `[manual]`** 任务（`- [ ] [manual]` 人工确认项被忽略），且 `## 待确认项` 为 `_暂无_`、无任何 `！！！` 批注、无 `## 追加任务` 的 `[open]` 条目时，在 execute 收尾同一轮：

- 将 `stage` 置为 `done`，`last_action` 记「任务全部完成，标记 done」。
- 在 `## 执行记录` 追加一条收尾条目。

`done` 是终止态：机器 / GUI 可据 `stage=done` 直接判定完成。此后不再自动推进；收到新增/扩展需求、新 bug，或 `## 追加任务` 出现 `[open]` 时，按「变更重开流程」切回 `plan`。

## new-spec

当 `spec_path` 缺省且无法从 session 上下文恢复时，自动生成路径与初始骨架。

### 步骤

1. **提炼摘要**：从用户输入提炼 kebab-case `summary-name`（≤ 40 字符，不以数字开头，必须语义化）。中文为主难以提炼时使用 `untitled-<NNN>` 占位。
2. **判定 type**：`feat` / `refct` / `fix`；prompt 中已显式给出时直接使用；不确定时询问用户，兜底取 `feat`。
3. **生成 id**：`YYMMDD.<type>.<summary-name>`（如 `260614.feat.spec-frontmatter`）。
4. **生成路径**：`<specsDir>/<id>/spec.md`。id 冲突时追加 `-2`、`-3` 后缀。
5. **初始化文档**：写入 frontmatter（`stage: plan`、`last_action: 新建 spec`、`updated_at` 本地秒级字符串、`summary` ≤ 200 字符）；建议创建全部章节（背景 / 需求 / 现状分析 / 技术实现方案 / 待确认项 / 任务清单 / 执行记录），将用户原始需求写入背景或需求。
6. **进入 plan**：初始化后在同一轮继续推进 plan，不要因为"文档已创建"就退出。

### CLI 触发模式

CLI/Service 同时给出 `类型：<type>` 与需求但未提供 `spec_path` 时，必须自动进入新建流程，不询问类型/路径；初始化后同一轮继续推进 plan，直到遇到真正阻塞才退出。
