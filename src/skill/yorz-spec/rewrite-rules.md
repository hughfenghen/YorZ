# 全局硬约束（含重开判定）

本文档列出任何阶段都必须遵守的硬约束、章节齐全度要求、以及"变更重开流程"的触发条件与处理方式。其它阶段文档默认这些约束已生效，请勿在阶段文档中重述细节，按需引用本文。

## 通用硬约束

- 仅更新目标 spec 文档，不修改无关文档。
- 每次写回文档都必须更新 frontmatter 元信息：`stage` / `last_action` / `updated_at` / `summary`。
- 执行任务时若涉及代码改动，必须只改动与任务相关的最小范围；每次写回都同时更新 frontmatter 元信息。

## 必备章节

若以下章节不存在，**先补齐再继续**：

- `## 现状分析`
- `## 技术实现方案`
- `## 待确认问题`
- `## 任务清单`
- `## 执行记录`

### 可选章节：`## 追加任务`

`## 追加任务` 由用户在 GUI/CLI 触发追加时懒插入，**不属于必备章节**：初始化 spec 与 lint `sections/required` 都不再要求其一定存在。若已存在，其位置固定在 `## 任务清单` 之后、`## 执行记录` 之前；spec-store 端 `mergeAppendTasksEntry` 会在首次追加时按该位置插入。

## 变更重开流程

### 触发条件

- 若在已有 spec 中识别到"新增/扩展需求"或"新增 bug"（无论来自正文变更或 `！！！` 批注），必须将 frontmatter `stage` 立即切回 `plan`，并在 `last_action` 记录"变更重开流程"。
- `## 追加任务` 章节存在 `- [open] [feat|refct|fix] ...` 条目时，视为"新输入"信号，必须将 `stage` 切回 `plan`，并按条目类型记 `last_action: 变更重开流程（追加任务：feat|refct|fix）`；多类型并存时以逗号串联（如 `feat,fix`）。

### 重开后必须做的事

- 变更重开后，必须仅针对新增内容重新走完 `plan -> tasks -> execute`：先补充分析与确认，再拆任务并执行。
- 未受影响的既有结论/任务可保留，但受影响任务必须重新评估与改写。
- 在 plan 阶段消费追加任务条目时，**不修改** `[open]` 状态标记，仅消费其内容；标记的更新发生在 [execute 阶段](./execute.md) 完成对应任务之后。
