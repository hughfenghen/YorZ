## 技术实现方案

### 总览

本期交付 2 个产物：

1. **`yorz-spec` skill 文件**：基于 `docs/ai-spec-drive-skill/SKILL.md` 改写为 YorZ 项目自有 skill，规范 Agent 执行 spec 驱动开发的工作流

### 项目工程化骨架

- 初始化 `package.json`
  - `name`: `@yorz/cli`（暂不发布 npm，仅本地 `npm link` 使用）
  - `private`: `true`（防止误发布）
  - `type`: `module`（ESM）
  - `bin`: `{ "yorz": "./dist/cli/index.js" }`
  - `engines.node`: `>=20`
  - `scripts`: `build` / `dev` / `test`
- 引入 TypeScript：`typescript` + `tsconfig.json`（target ES2022、module NodeNext、moduleResolution NodeNext、strict）
- 构建：**Vite**（lib 模式）
  - 入口：`src/cli/index.ts` → 产物 `dist/cli/index.js`
  - 通过 `?raw` 在编译期把 `src/skill/SKILL.md` 内联为字符串常量（避免运行时定位文件路径，且打包结果自洽）
  - `build.rollupOptions.external`：Node 内置模块 + `commander`
  - 添加 shebang banner `#!/usr/bin/env node`
  - 同时把 `src/skill/SKILL.md` 原样复制一份到 `dist/skill/SKILL.md`（便于调试 / 后续脚本读取）
- 单测：**vitest**（与 vite 共享配置）
- CLI 解析：`commander`
- 文件操作：Node 内置 `fs/promises` + `path` + `os`
- 代码格式化：`prettier`，纳入 `npm run format`
  - `.prettierrc.json`：开启 `proseWrap: "preserve"`、`printWidth: 100`，以保证 md 写回时换行可控

### CLI 设计

#### 命令

```
yorz install   [--agent <claude|opencode>] [--scope <user|project>]
yorz uninstall [--agent <claude|opencode>] [--scope <user|project>]
```

- 默认 `--agent claude`，默认 `--scope user`
- `install` 行为（默认覆盖；与架构文档第 6 节决策一致）：
  1. 通过适配器解析目标 `<base>/yorz-spec/SKILL.md`
  2. 确保目录存在（`mkdir -p`）
  3. 直接写入内联的 SKILL.md 字符串内容（覆盖已存在文件）
  4. 打印 `installed: <absolute path>`
- `uninstall` 行为：
  1. 解析目标 `<base>/yorz-spec/`
  2. 若存在则 `rm -rf` 该目录
  3. 若不存在则打印 `not installed at <path>` 并退出 0

#### Agent 适配器接口

```ts
interface AgentAdapter {
  name: 'claude' | 'opencode'
  resolveSkillsDir(scope: 'user' | 'project', cwd: string): string
}
```

- `claude` 适配器：
  - user → `path.join(os.homedir(), '.claude', 'skills')`
  - project → `path.join(cwd, '.claude', 'skills')`
- `opencode` 适配器（一级支持）：
  - user → `path.join(os.homedir(), '.config', 'opencode', 'skills')`
  - project → `path.join(cwd, '.opencode', 'skills')`
  - 不再标记 experimental

#### Skill 资源寻址

- 通过 Vite 的 `?raw` 在编译期将 `src/skill/SKILL.md` 转为字符串导入：
  ```ts
  import skillContent from '../skill/SKILL.md?raw'
  ```
- 运行时直接将 `skillContent` 写入目标路径，CLI 不依赖任何运行时文件查找逻辑

> - `## 流程状态` 章节**完全删除**，避免双源

**背景**：当前 `src/skill/SKILL.md` 规定 spec 文档以 `## 流程状态` 章节、扁平 `- key: value` 列表记录元信息（当前阶段 / 最近动作 / 更新时间）。该方案与 markdown 正文耦合，存在以下问题：

- 元信息以散文列表写在 body 中，工具（FS Watcher、未来 Service GUI）需要按文本规则解析，脆弱
- 结构与正文章节平级，不利于一眼区分"机器可读元信息"与"人读叙述"
- 无"总结"字段，外部工具（如列表视图）需要再次读取正文才能展示概要

**现状分析（针对本 bug）**：

- yorz-spec skill 是 spec 文档结构的唯一约束源；改 skill 即改全部 spec 的格式约定
- 本 spec（`docs/specs/260611.feat.init-cli-and-skill.md`）自身需要在改动落地后迁移到新格式，作为示范
- `src/skill/SKILL.md` 经 Vite `?raw` 内联进 CLI 产物，skill 文本改动须重新 build 才会生效；已发布的安装包用户需 `yorz install` 覆盖

**技术实现方案（针对本 bug）**：

1. **新增 spec 文档 frontmatter 规范**，写入 `src/skill/SKILL.md`：

   ```yaml
   ---
   stage: plan # plan | tasks | execute
   last_action: 简述上一次动作
   updated_at: 2026-06-14 # YYYY-MM-DD
   summary: 一句话概要，供列表/索引视图展示
   ---
   ```

   - 字段使用英文键名（与 skill 自身 frontmatter 风格一致，便于工具静态解析）
   - 字段值允许中文
   - `summary` **必填**，长度 ≤ 200 字符；不允许空字符串

2. **移除 `## 流程状态` 章节**：

   - 在 skill 的「全局硬约束」「自动模式判定顺序」「Markdown 格式化约定」「输出优先级」中将所有"`## 流程状态`"相关描述替换为"frontmatter 元信息"
   - 必备章节列表去掉 `## 流程状态`；保留 `## 现状分析` / `## 技术实现方案` / `## 待确认问题` / `## 任务清单` / `## 执行记录`

3. **每次写回的硬约束改写为**：

   - 必须更新 frontmatter 的 `stage` / `last_action` / `updated_at` / `summary`
   - 字段缺失时先补齐再继续
   - 时间字段仍使用 `YYYY-MM-DD`

4. **Markdown 格式化约定补充**：

   - frontmatter 字段顺序固定为 `stage` → `last_action` → `updated_at` → `summary`
   - 每个字段独占一行，禁止嵌套
   - 写回后调用 prettier 时，确保不破坏 frontmatter

5. **同步迁移本 spec 自身**：在执行阶段，将本文件顶部加上对应 frontmatter，并删除 `## 流程状态` 章节，以作示范

6. **构建与分发**：修改 `src/skill/SKILL.md` 后需 `npm run build` 重新打包；执行记录补充本次构建结果

7. **不保留旧格式兼容**：skill 不再解析旧 `## 流程状态` 章节；现有 spec 一次性迁移完成

### 变更补充（2026-06-14b）：`spec_path` 非必填与默认目录

> 第二轮批注已确认（消费）：
>
> - 子目录布局 `.yorz/specs/<id>/spec.md`
> - `summary-name` 由 Agent 自动从需求摘要提炼（kebab-case，≤ 40，仅 `[a-z0-9-]`，不以数字开头）
> - `type` 默认 `feat`；不确定时显式询问用户
> - id 冲突时追加 `-2`/`-3` 数字后缀
> - 不写入 `.gitignore`，由用户决定是否提交
> - 本 spec 自身在 execute 阶段同步迁移到新 frontmatter 结构作示范

**背景**：当前 `src/skill/SKILL.md` L12 规定 `spec_path` 为必填。需求扩展为允许"空 spec_path 调用"——此时 skill 应自行生成 id 与路径，把新 spec 落到 `.yorz/specs/<id>/spec.md`。

**现状分析（针对本需求）**：

- 现有调用形式：`/yorz-spec <spec_path>`，spec_path 缺省即报错或要求补齐
- 新增场景：用户起一个新需求，但不想自己决定文件位置（典型于 `yorz init` 之后的新建流）
- 文件 id 命名规则（用户已明确）：`YYMMDD.(feat|refct|fix).<summary-name>.md`
  - 例：`260614.feat.spec-frontmatter.md`
  - `YYMMDD` 取当前日期；`type` 取自需求性质；`summary-name` 由 Agent 从需求摘要生成的 kebab-case
- `.yorz/specs/` 目录之前在架构文档 (`docs/Architecture.md`) 中被提及为 spec 存放位置之一

**技术实现方案（针对本需求）**：

1. **修改 skill 输入约定**（`src/skill/SKILL.md`）：

   - `spec_path`：**可选**；省略时 skill 进入"新建 spec"流程
   - 新增字段语义：
     - 当存在 `spec_path` 时，行为不变（更新现有 spec）
     - 当缺省 `spec_path` 时：
       1. 从首轮用户输入提炼需求摘要 → 生成 `summary-name`（kebab-case，≤ 40 字符，仅 `[a-z0-9-]`）
       2. 由需求性质决定 `type ∈ {feat, refct, fix}`
       3. 取当前日期 `YYMMDD`
       4. 拼接 id：`YYMMDD.<type>.<summary-name>` → 文件路径 `.yorz/specs/<id>/spec.md`
       5. 若目标文件已存在，追加 `-2`、`-3` …… 数字后缀避免覆盖
       6. 创建目录与文件，并初始化 frontmatter（stage=plan、updated_at、summary）+ 六大章节空骨架
       7. 进入 `plan` 阶段
   - 在 skill 中新增 `## 新建 spec` 一节专门约束该流程

2. **type 取值判定指引**：

   - 引入新功能 → `feat`
   - 重构 / 重写 / 抽取 → `refct`
   - 修复缺陷 → `fix`
   - 不确定时：**显式询问用户**；若强制兜底则默认 `feat` 并在 `summary` 中标注"待确认 type"

3. **目录约定**：

   - 单 spec 落在 `.yorz/specs/<id>/spec.md`（每个 spec 一个独立子目录，便于后续放置附件/截图/中间产物）
   - skill 自身不写入 `.gitignore`；是否提交 `.yorz/specs/` 由用户自行决定

4. **与 CLI 关系**：

   - 本期 CLI 不变；该需求只影响 skill 文本与运行时行为
   - `npm run build` 会将更新后的 skill 重新内联进 `dist/cli/index.js`

5. **同步示范**：本 spec 文件名为 `260611.feat.init-cli-and-skill.md`，符合命名规则；不迁移路径（保留在 `docs/specs/`，因其早于 `.yorz/specs/` 约定）；新建 spec 才走 `.yorz/specs/<id>/spec.md`；本 spec 在 execute 阶段同步加上 frontmatter 并删除 `## 流程状态` 章节作示范
